# Primary keys

How internal records get their IDs, why Discord snowflakes stay `bigint`, and
what a new table owes the schema.

Internal records use prefixed-UUID string PKs (`srv_<uuid>`, `plg_<uuid>`, …),
generated by a Postgres column **default**:

```ruby
execute "ALTER TABLE x ALTER COLUMN id SET DEFAULT ('srv_' || gen_random_uuid())"
```

set inside a `reversible { dir.up { … } }` block in the table's migration.
ActiveRecord omits `id` on insert and reads it back via `RETURNING`. An inline
expression (not a named function) is used so the default round-trips through
`schema.rb` — a named function would force `schema_format = :sql` and add
`pg_dump`/`psql` to the images. `gen_random_uuid` is Postgres-core (no extension).

Discord snowflakes (`discord_id`, `user_id`, `channel_id`, `role_id`,
`message_id`, `server_id`) stay `bigint` — they're external identifiers, not our PKs.

Model validations and DB constraints must mirror each other (CI enforces this via
`active_record_doctor`). Index foreign keys and read paths on new tables.

Enum-like string columns use the `string_enum` macro (`ApplicationRecord`), which
maps each value to its identical string and validates membership instead of raising
on assignment — a bad web param fails through the normal validation path. Keep the
column's `IN (...)` DB check constraint alongside it. Pass `prefix: true` whenever a
value would collide with an Active Record method (`none` always does); columns that
are `NOT NULL` without a default also keep an explicit `presence` validator and pass
`validate: {allow_nil: true}` so nil reports "can't be blank" and doctor sees the
mirror.
